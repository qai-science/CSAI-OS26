Semaphores in depth

  

    

      

        
What a semaphore is

        
A semaphore is a non-negative integer plus a queue of sleeping processes, kept by the kernel. Edsger Dijkstra introduced it in 1965 with two operations, P (proberen, "try") and V (verhogen, "raise"). POSIX calls them sem_wait and sem_post.

        
sem_wait(S):            // P, "down"
    if S.value > 0:
        S.value = S.value - 1     // take one, go on
    else:
        sleep in S.queue          // no CPU used

sem_post(S):            // V, "up"
    if S.queue is not empty:
        wake one sleeper          // it takes the unit
    else:
        S.value = S.value + 1

        
Each operation is atomic: the check and the change happen as one indivisible step. Without that, two processes could both see value == 1 at the same instant, and both would walk in.

      

      

        
Three ways to use one

        
    
          
  • init 0Signalling. "Something has happened." The waiter sleeps until another process posts. This is the Semaphore: fix the race tab.
    • 
          
  • init 1Mutual exclusion (a binary semaphore). Call wait before the critical section and post after it, so only one process is inside at a time.
    • 
          
  • init NCounting resources. N identical things, such as printers, connections or buffer slots. This is the Counting semaphore tab.
    • 
        

        
Semaphore vs mutex

        
A mutex has an owner: only the thread that locked it may unlock it. A semaphore has no owner. Any process may post, and that is exactly what makes signalling between different processes possible.

        
Producer and consumer

        
The classic bounded buffer with N slots uses three semaphores: empty = N, full = 0 and mutex = 1. The producer does wait(empty), wait(mutex), put, post(mutex), post(full). The consumer does the mirror image. A pipe does all of this for you inside the kernel.

      

    


    
The POSIX API

    

      
CallWhat it does

      
sem_open(name, O_CREAT, mode, value)Creates or opens a named semaphore (Linux shows it as /dev/shm/sem.NAME). value is used only when it is created.

      
sem_init(&s, pshared, value)An unnamed semaphore. Use pshared = 1 and place it inside shared memory to share it between processes.

      
sem_wait(s)Decrements, or blocks while the value is 0.

      
sem_trywait(s)Like sem_wait but never blocks. It fails with EAGAIN when the value is 0.

      
sem_timedwait(s, &deadline)Blocks until an absolute time, then fails with ETIMEDOUT.

      
sem_post(s)Increments, or wakes one waiter. It is async-signal-safe, so it can be called from a signal handler.

      
sem_getvalue(s, &v)Reads the current value. It may already be out of date when you look at it, so use it for debugging only.

      
sem_close / sem_unlinkclose drops this process's handle. unlink removes the name. Compile with -pthread.

    


    
Common mistakes

    
    
      
  • Forgetting sem_post on an error path. Every later sem_wait then sleeps forever.
    • 
      
  • A stale named semaphore. If an earlier run crashed, sem_open(..., O_CREAT, ..., 2) silently reuses the old value. That is why sem_counting.c calls sem_unlink first.
    • 
      
  • Deadlock. P1 holds A and waits for B, while P2 holds B and waits for A. Always take semaphores in the same global order.
    • 
      
  • Posting more than you wait. The value climbs above 1, and a "lock" stops excluding anyone.
    • 
      
  • Busy waiting (while (flag == 0) ;) instead of a semaphore. It burns a CPU core and is still not safe without atomic operations.
    •
